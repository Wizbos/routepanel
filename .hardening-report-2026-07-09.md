# Pi-hole forward-fragment sync hardening — 2026-07-09

## Incident

Corporate installation: the panel's `/pihole-forward.conf` endpoint served a
malformed fragment; the site Pi-hole's pull-cron script applied it without
validation and restarted pihole-FTL -> dnsmasq "Name does not resolve at line
3" -> FAILED to start -> site DNS dead for 20 minutes until the next fragment
change.

## What exists in this OSS repo (and what doesn't)

There is **no** `pihole-forward.conf` HTTP endpoint, no `pull-cron` script,
and no Pi-hole-specific code anywhere in `Wizbos/routepanel`
(`grep -rli pihole .` over the whole tree, excluding `.venv`/`.git`, returns
nothing). The corp deployment's "site Pi-hole polls an HTTP endpoint and
applies it with a bash cron script" pattern is a downstream customization
that was never contributed back upstream.

The OSS architecture is different and simpler: routepanel and dnsmasq run on
the **same box** (the VPS). The daemon (`routesyncd`,
`src/routepanel/syncd/main.py`) builds the ipset-tagging fragment in-process
and writes it straight to
`/etc/routepanel/dnsmasq-routepanel.conf` (`config.dnsmasq_conf_path`), which
`/etc/dnsmasq.d/routepanel-base.conf`'s `conf-file=` directive pulls in. The
"sync script" is Python, not bash:

- `src/routepanel/syncd/dnsmasq_manager.py`
  - `render_fragment(rules)` — builds `ipset=/dom1/dom2/.../rule_<id>` lines
    from each domain rule's `domains` JSON column.
  - `write_fragment(path, content)` — atomic write (`tempfile` + `os.replace`).
  - `reload_dnsmasq(service)` — `systemctl reload dnsmasq`.
  - `sync_fragment(path, service, rules)` — orchestrates the above, called
    every `routesyncd` cycle from `main.py` (`_run_sync_inner`).

So "port the corp hardening, adapted" meant reimplementing the same
validate-before-apply / last-known-good logic as Python inside
`sync_fragment`, using `dnsmasq --test` (plain dnsmasq's documented syntax
checker, reading the same default config-dir chain that includes our
fragment) as the equivalent of `pihole-FTL dnsmasq-test`. This was not
independently verified against a live dnsmasq binary in this session (no
Ubuntu/dnsmasq host available here) — the corp incident's live verification
only covered `pihole-FTL dnsmasq-test` on v5.18/v6.4, not plain dnsmasq's
`--test` flag. Flagging as the one part of this change that should be
smoke-tested against a real `dnsmasq` binary before the next `install.sh`/
`setup-dns.sh` run in production.

## Changes

### 1. `src/routepanel/syncd/dnsmasq_manager.py` — validate-before-apply + LKG

- Added `check_config()`: runs `dnsmasq --test`, returns `rc == 0`.
- Rewrote `sync_fragment()`:
  1. Render the fragment; if unchanged, return `False` immediately (no
     validate/reload — matches the original no-op-on-unchanged behavior).
  2. If the fragment currently on disk exists, snapshot it to
     `<path>.lkg` **before** overwriting (this is the "last known good" —
     the previously-applied, presumed-working fragment).
  3. Write the new content.
  4. Run `check_config()`. On failure: restore `<path>.lkg` if it exists,
     else remove the just-written bad fragment (never leave known-bad
     content in place); log via the module's logger (`routesyncd`, already
     journal-integrated under the `routesyncd` systemd unit — no separate
     `logger -t` shell-out needed, unlike the corp bash script which had no
     other logging path); return `False`. **Never reload on failure.**
  5. On success: `reload_dnsmasq()`, log, return `True`.
- Added domain re-validation inside `render_fragment()` itself (see below) —
  defense in depth so a bad row already in the DB (pre-dates this change, or
  written directly to SQLite outside the API) can't corrupt the fragment
  even before `sync_fragment`'s LKG guard kicks in.

### 2. Generator-side sanitization — `src/routepanel/domainval.py` (new)

**Could the generator really emit garbage? Yes, concretely:**

`render_fragment` built each line as
`"ipset=/" + "/".join(domains) + "/rule_<id>"` straight from the
user-supplied `domains` JSON array, with **zero validation**. Given the
`/`-delimited, `#`-comments dnsmasq config-line format, a rule domain
containing:

- **`/`** — adds an extra field, e.g. `evil.com/rule_1` as one domain string
  turns the line into `ipset=/evil.com/rule_1/rule_5`, structurally
  ambiguous/wrong versus the intended set target — this is exactly the class
  of malformed line dnsmasq choked on in the incident.
- **whitespace** — a bare space is generally tolerated as line-continuation
  garbage by dnsmasq's tokenizer in some contexts but is not a valid domain
  character and is the most likely direct repro of "Name does not resolve".
- **a literal newline (`\n`)** — the most severe case: since the fragment is
  just `"\n".join(lines)`, a domain string containing `\n` injects an
  **entirely new line** into the config file — i.e. arbitrary dnsmasq
  directive injection, not just a syntax error. Anyone who can create a
  domain rule (panel is single-password-gated, but still) could plant a
  hostile directive.
- **empty string** — produces a bare `/` sequence (`//` or a leading/trailing
  `/`), an empty domain field.
- **`#`** — dnsmasq treats `#` as start-of-comment; a domain containing `#`
  truncates the rest of the line, which for this format means **the
  `/rule_<id>` suffix gets eaten as a comment**, leaving a directive with no
  ipset target.
- **non-ASCII garbage** — not RFC-1035 label characters; likely a parse
  failure, and not clearly defined dnsmasq behavior either way.

None of the existing 144 tests or `service_library.json` entries exercised
this — every seeded/tested domain was already well-formed, so the gap was
silent.

`src/routepanel/domainval.py` (new module, mirrors the CIDR validation
precedent in `src/routepanel/cidr.py`):

- `is_valid_domain(value)` — ASCII-only, no leading/trailing whitespace,
  non-empty, `<= 253` chars, matches an RFC-1035-shaped dotted hostname
  (`label(.label)+`, labels alnum+hyphen, hyphen never leading/trailing).
  This regex structurally excludes `/`, internal whitespace, `#`, and control
  characters, since none are valid label characters.
- `validate_domains(values)` — raises `ValueError` naming the first bad entry
  (same contract as `cidr.normalize_cidrs`), for the panel API to turn into
  HTTP 422.
- `filter_valid_domains(values, on_invalid=None)` — drops invalid entries,
  optionally calling `on_invalid(value)` per drop, for the generator's
  defense-in-depth pass (does not raise — a bad row already in the DB must
  never break the whole fragment).

Wired up at **both** layers per the task's (a)+(b) option:

- **(a) Generation**: `render_fragment()` now calls `filter_valid_domains()`
  per rule before building its `ipset=` line, logging each dropped domain
  (`log.warning(... "skipping invalid domain %r in rule %s" ...)`). A rule
  whose domains are *all* invalid is skipped entirely (same as the existing
  empty-domains behavior).
- **(b) Rule creation**: `src/routepanel/panel/routes/domains.py`'s
  `add_domain_rule` (POST `/domains`) and `update_domain_rule` (PUT
  `/domains/{id}`) both call `validate_domains(data.domains)` before touching
  the DB, returning HTTP 422 on the first bad entry — mirrors the existing
  `static_cidrs` validation via `normalize_cidrs` immediately below it.

`src/routepanel/panel/routes/library.py` (the service-library "packs"
catalog) was deliberately **not** touched: packs never feed
`render_fragment` directly (only `domain_rules` rows do), they're just
templates the UI copies into a POST `/domains` call, which is now validated.
Confirmed via `grep -rn "INSERT INTO domain_rules"` — the only insert path is
`add_domain_rule`.

## Tests

New/changed files:

- `tests/unit/test_domainval.py` (new) — `is_valid_domain` accept/reject
  matrix (slash, space, empty, newline, `#`, non-ASCII, oversized, wrong
  type, valid incl. punycode IDN); `validate_domains` raise-on-bad-entry +
  empty-list-ok; `filter_valid_domains` drop-and-keep + `on_invalid` callback.
- `tests/unit/test_dnsmasq_manager.py` (extended) — `render_fragment` drops
  an invalid domain but keeps the rest of the rule's line; a rule with only
  invalid domains is skipped entirely; every non-comment output line is
  structurally verified to parse as `ipset=/dom[/dom...]/rule_N` with no
  empty/space-containing domain fields. `sync_fragment`: unchanged content
  skips validate+reload; valid new content installs and reloads; invalid new
  content is rejected, last-known-good is restored, reload never called; no
  prior LKG -> bad fragment is removed rather than left in place;
  `check_config()` calls `dnsmasq --test` and maps `rc==0`/`rc!=0` correctly
  (mocked `subprocess.run`, since no dnsmasq binary here).
- `tests/api/test_domains.py` (extended) — POST/PUT `/domains` reject a
  domain containing `/` or a space, and an empty domain entry, with 422;
  a domains-`[]` static-CIDR-only rule is still accepted (unchanged
  behavior); a rejected PUT leaves the original rule untouched.
